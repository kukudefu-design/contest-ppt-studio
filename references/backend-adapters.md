# 按能力编排制作后端

## 选择之前

从当前会话技能目录、可用工具和实际安装位置发现能力，不假设本文件旁边存在其他 skills，也不硬编码开发者电脑路径。只读取选中后端与当前任务相关的说明。

至少检查：材料读取、图片预览、生图/抠图、原生文本与图表、逐字矢量、逐对象动画、最终PPTX渲染、指定软件验证。将“说明中宣称支持”“依赖可用”“已在本项目实测”分开。

没有任何第三方后端时仍可完成材料诊断、需求整理和内容方案；不能凭这些产物宣称完整制作能力已具备。给出缺项和最小解决方案，不强制装一套无关工具。

## PPT Master（可用时优先评估）

项目来源：[hugohe3/ppt-master](https://github.com/hugohe3/ppt-master)。使用宿主实际提供的 skill 位置，读取入口；如其版本要求，先运行 `scripts/attribution_guard.py`，失败即停止该后端，不绕过或修改它；Python 命令采用环境真实解释器。

通过后读该版本 `workflows/routing.md`，按请求选一个生命周期：

- 新建或设计重构通常是生成流程；将已确认需求、风格和来源作为有效输入。
- 固定官方原生模板的填充/局部编辑通常应使用保留原生设计的编辑流程，不通过整页重绘破坏模板。
- 只有用户要求可重复使用的模板资产时才做模板创建；单次比赛PPT不自动扩展成模板平台。

以本机当前文档为准，不能把这些示例当成永不变化的命令：现有版本可提供 SVG→原生PPTX、文字轮廓、自定义几何、原生图表和逐对象动画。实际调用前确认依赖、字体和输入契约。

对象动画需求应触发其逐页/逐对象配置流程；当前版本相关入口包括 `workflows/stages/customize-animations.md`、`references/animations.md` 和 `scripts/animation_config.py`。只用全局 `auto` 不能证明已完成用户要求的精细编排；配置目标必须来自实际对象，校验后导出再读回。

**适配覆盖清单**：向后端显式传入本次已确认要求：未知风格三张三页展板、已知风格一张三页展板、主标题逐字矢量、尽可能全部原生、逐元素动画、指定软件、完整项目包。若后端默认使用图片艺术字、关闭对象动画或增加不同风格门，不得静默覆盖用户要求；以用户明确要求为准，技术不支持则说明缺口并换适配路线。

不要修改后端 skill、跳过其完整性检查，或把其代码复制进本 skill 来规避依赖。保留实际调用版本、命令、输出和必要中间文件。

## 设计与图片能力

可用设计 skill（例如 [huashu-design](https://github.com/alchaincyf/huashu-design)）用于版式、素材和风格探索。导出 HTML 动画不等于 PPTX 对象动画；导出 HTML 图片不等于最终 PPTX 渲染。分别核对图表、字体、形状和动画的真实输出。

仅吸收本次需要的能力；不要复制整套流程造成重复询问。用户已指定风格时遵守本 skill 的一张三页展板要求。不要自动继承其他 skill 的偏好采集、长期记忆、版本更新或无关外部操作。

生成图片或编辑抠图时使用当前可用的专用图片工具与对应技能；按它的输入/引用约束执行。保留最终图片、用途、来源或必要生成说明。为背景生成意象，不能为项目补造试验、合影或获奖证据。

## 通用原生后端

若采用其他原生制作库、PptxGenJS、python-pptx、OOXML或可用的宿主工具，先读当前官方/本地文档并做小范围验证。不能默认某库支持所有动画、可编辑图表和矢量艺术字。

需要针对性 OOXML 处理时，编辑副本，保持资源关系、对象ID、顺序和格式有效，并保留原始文件及修改源代码。不能把手工插入 `p:timing` 的存在当成动画播放已通过。

## 依赖与故障处理

不因 GitHub 星数而自动安装；先核实来源、许可、能力和安装影响。缺依赖时优先复用现有工具或任务内隔离依赖；外部付费、账户注册、全局配置及覆盖其他 skills 需要在实际动作前获得相应授权。

固定一次失败的具体原因，做有依据的修复；同一原因连续两次失败就汇报证据并换可满足要求的路线，若替代会降低核心编辑性、取消图片或对象动画，则先让用户选择。可独立进行的内容诊断和需求整理继续。

依赖不足时输出：缺失能力、受影响阶段、已完成产物、补齐或替换选项、需要的用户决定。仅缺 PowerPoint/WPS 实机验证时保留明确“待验证”交付状态，附操作清单。
